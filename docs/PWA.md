# PWA and offline behaviour

How `docs/` is packaged so the phone UI installs and runs with no signal.

## Why

Web Bluetooth, geolocation and the screen wake lock all require a **secure
context**, which in practice means loading the page over https. A range walk
takes you away from signal by definition — that is the thing being measured —
so the one situation the page is built for is the one where it cannot be
loaded.

Installing the GitHub Pages copy keeps the `https://` origin, and everything it
unlocks, available with no network. Nothing else about the app changes: it
still talks to the boards over Bluetooth, which never needed the internet.

There is no second, locally-served copy to worry about here (unlike the
Moonshot Avionics dashboard, which also has an HTTP copy served off a base
station). The PWA is the whole story.

## Files

| File | Role |
|---|---|
| `manifest.webmanifest` | Name, icons, `display: standalone`. All paths relative, so the app can move to a different path or domain untouched. |
| `sw.js` | Service worker: precache + stale-while-revalidate. |
| `icons/` | Generated by `make_pwa_icons.py` at the repo root. |
| `.nojekyll` | Disables Jekyll on GitHub Pages, so nothing in `docs/` can be silently dropped by its default exclude list. |

The app itself is still one self-contained `index.html` — all CSS and JS
inline, no libraries, no runtime fetches. The precache list is therefore the
page plus the manifest plus six icons, and there is nothing that can go missing
offline.

## Caching strategy

`sw.js` precaches on install, then serves same-origin GETs
**stale-while-revalidate**: cache first (instant, and correct when offline),
refresh in the background, and post a message to the page if the bytes on the
server changed, which raises a tap-to-reload prompt.

Deliberately *not* network-first: out in a field there is often a bar of signal
that resolves DNS and then stalls, and a network-first page would stall with
it.

Two details that are load-bearing:

- **A launch checks `index.html` explicitly.** A reload does not reliably route
  subresources through the worker — Chrome can answer them from the renderer's
  memory cache — so the page asks the worker to re-check on startup. It is a
  conditional request, so a few hundred bytes of 304 when nothing changed, and
  nothing at all when offline.
- **`ev.waitUntil()` is called synchronously** from the fetch handler. Call it
  from inside a `.then()` and the event may already have finished, which throws
  and silently kills the background refresh.

`CACHE_VERSION` in `sw.js` does **not** need bumping for ordinary edits —
stale-while-revalidate picks those up. Bump it only to force-evict every
client, e.g. after removing a precached file.

## Sharing an origin with the other app

`bucketshoes.github.io` also hosts the Moonshot Avionics dashboard, under
`/MoonshotAvionics/`. Service worker **scopes** are per-directory so the two
workers never handle each other's requests, but two things are origin-wide and
have to be namespaced by hand:

- **The cache store.** This app's caches are prefixed `esprangetest-`, and both
  the activate cleanup and the purge below only ever delete caches carrying
  that prefix.
- **`navigator.serviceWorker.getRegistrations()`**, which returns *every*
  registration on the origin. The recovery hatch filters by scope before
  unregistering anything.

Get either wrong and resetting one app silently destroys the other's offline
copy — which you would only discover the next time you were somewhere with no
signal.

`localStorage` is also origin-wide, but the keys do not collide: this app uses
`esprt.*` and the dashboard uses `base-url` and `cmd-nonce`.

## Recovery

Loading `…/?nosw` clears this app's offline copy and unregisters its worker.
This exists because a bad cached build would otherwise survive every reload,
and halfway up a hill there is no dev-tools escape.

The order matters. The page asks the worker to purge **first** and only
unregisters once the worker confirms, because the navigation that loaded
`?nosw` also kicked off a background revalidate — and its `cache.put()` landing
after a delete would quietly recreate the cache. The worker sets a `purging`
flag that stops it writing and stops it intercepting, deletes its own caches,
then replies. A three-second timeout covers a wedged or already-dead worker.

## Gotchas

- **The PWA's identity is its path.** Moving the page elsewhere installs as a
  *new* app; the old install keeps pointing at the old URL until removed.
- **iOS installs from Safari only**, via Share → Add to Home Screen — and iOS
  Safari has no Web Bluetooth at all, so the app cannot connect to a board
  there. This is an Android/desktop Chrome tool, same as before.
- **New file in `docs/` that the page needs to boot → add it to `PRECACHE`**
  in `sw.js`, or it will 404 offline.
